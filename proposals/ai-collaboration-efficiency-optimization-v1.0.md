# AI 协作开发效率优化提案 V1.0

- **状态：** PROPOSED / 待试点验证
- **适用范围：** 可复用于不同软件项目、团队及 AI 协作工具的协同开发流程
- **性质：** 非规范性改进提案；不自动修改现行标准、任务合同、授权或已接受基线
- **形成日期：** 2026-11-04

## 1. 目标与原则

本提案希望减少 AI 协作开发中的重复核查、重复交接、上下文恢复成本、无效阻塞尝试和人工调度等待，让协作从依赖对话记忆与反复确认，转向**持久状态驱动、实际证据驱动、按依赖并行、按风险治理**。

效率优化不以增加文档、流程、角色或工具数量为目标。优先复用项目已有的任务台账、仓库文档、Issue、PR、执行日志和模板。所有改进必须兼容项目当前的授权与验收规则；未经授权不得变更目标、Contract、共享资源或高风险操作边界。

## 2. 与现行协作职责的兼容

本提案沿用三层责任模型，不增加新的权力层级：

- **Controller / 总控：** 管理目标、授权、优先级、跨组资源与依赖协调、重大变更、集成和最终接受。
- **Middle Layer / 中间层：** 在授权内将任务转成可执行合同，协调执行工具，核查证据、集中纠错、维护状态并向总控提供决策材料。
- **Coding Tool / 执行工具：** 按合同实施并自检，报告实际变更、命令、结果和未完成事项。

效率机制只能减少重复劳动，不能转移最终决策权。中间层不得默默改变目标、验收标准、共享 Contract 或跨组资源决定；执行工具不得扩大范围或自行宣称最终接受。

## 3. 持久化任务状态：单一当前视图，而非单一事实源

建议每个任务维护一份简洁的当前状态记录，供新对话、接手人员和执行工具快速恢复。状态记录是**导航与汇总视图**，不是授权、合同、仓库事实或原始证据的替代品。

建议字段：

- TASK_ID、ROUND_ID、STATUS、CURRENT_OBJECTIVE
- AUTHORIZATION / CONTRACT 位置
- ACCEPTED_BASELINE / 相关证据指针
- OWNER、WORKSPACE、BRANCH、HEAD（按任务需要）
- LAST_RESULT、EVIDENCE、BLOCKER、RECOVERY_CONDITION
- REMAINING_WORK、NEXT_ACTION、UPDATED_AT

事实与权威顺序应遵循项目现行标准。通常，正式授权与有效合同决定允许做什么；真实仓库、环境和执行结果决定实际发生了什么；已接受记录及其证据决定可信基线；状态卡只索引这些信息。历史对话与 AI 记忆不能覆盖正式记录。状态卡与证据冲突时，先标明冲突并核实，不得仅凭状态标签宣布 PASS。

## 4. 已接受基线与增量核查

已正式接受的工作应作为后续任务的可信基线。后续任务不应无理由重做、重测或重构前序工作。

仅在出现以下情况时，针对受影响的最小范围重新核查：当前行为与合同冲突、发现回归、当前任务被实际阻塞、明确安全或数据完整性问题，或获得重新审查授权。

处理基线问题采用可追踪的最小闭环：Finding → 影响范围 → 最小修复 → 针对性验证 → 返回当前任务。不得借局部问题扩展为无关重构。此原则不免除当前任务对自身交付物和必要集成验证的责任。

## 5. 三类信息交接

建议将长期状态、本轮指令和本轮结果分开，避免每次交接复制整个历史。

### 5.1 TASK_STATUS：长期状态

记录当前目标、状态、已接受内容、剩余工作、阻塞及下一动作；保存正式合同和证据链接，不复制冗长执行日志。

### 5.2 EXECUTION_TASK：本轮执行合同

按现有项目模板填写，至少明确：

- TASK_ID / ROUND_ID / RECIPIENT
- WORKSPACE / BASELINE / CONTRACT
- OBJECTIVE / AUTHORIZED_SCOPE / OUT_OF_SCOPE
- REQUIRED_ACTION / DEPENDENCIES / STOP_CONDITIONS
- VERIFY / DELIVERABLE / REPORT_TO

必须明确执行对象和准确工作目录；关键业务规则、授权和验收条件不能留给工具猜测。

### 5.3 EXECUTION_RESULT：本轮实际结果

按任务风险记录实际执行方、工作区、分支与 HEAD、变更文件、执行命令、测试环境与结果、退出码、失败/跳过/未执行项、证据位置、提交/推送/集成状态、阻塞和下一动作。

严格区分 IMPLEMENTED、SELF-VERIFIED、INDEPENDENTLY-VERIFIED、COMMITTED、PUSHED、INTEGRATED 与 ACCEPTED/CLOSED。前一状态不自动证明后一状态。已有项目模板可直接满足这些字段时，不另造重复模板。

## 6. 状态驱动与事件式恢复

可将项目现有状态映射为以下执行策略；不得为采用本提案而强制更改已有状态词汇：

| 当前情形 | 默认动作 |
|---|---|
| 前置条件齐全、可执行 | 进入执行队列，按优先级启动 |
| 正在执行 | 跟踪当前轮次，不重复派发同一工作 |
| 已交付、待核查 | 根据验收标准核验证据 |
| 明确阻塞 | 记录阻塞责任方、受影响范围、恢复条件与恢复后动作 |
| 等待外部事件/依赖 | 等待条件变化；不重复尝试相同失败操作 |
| 已接受/关闭 | 作为可信基线保存，不重新打开，除非触发明确复查条件 |

阻塞记录应简明回答：缺少什么、为何必需、已完成哪些不依赖该条件的工作、哪些操作停止、恢复条件是什么、条件满足后第一步做什么。出现恢复事件后重新判断是否可执行。无新证据、条件或授权变化时，不重复同一尝试。独立任务可以继续；局部工作包完成不代表整体任务已满足验收。

## 7. 风险匹配与并行准备度

流程重量应匹配任务风险，而不是所有任务采用同等文档和确认成本。项目可采用轻量/标准/审慎等分级，但需映射既有安全政策：

- **低风险、边界明确、可回退：** 使用简短合同与必要验证。
- **跨模块、接口或数据影响：** 明确依赖、合同、执行结果及独立核查范围。
- **权限、数据删除/迁移、生产环境、安全或其他高风险操作：** 明确授权、执行前确认、审计和回滚/恢复要求。

并行前检查依赖成熟度、唯一负责人、工作区隔离、文件冲突、共享环境和接口合同。同一文件或共享资源原则上协调后串行；依赖未成熟时可先推进独立工作，但不能猜测接口或越权写入共享环境。并行的目标是缩短依赖等待，而不是同时启动更多工具。

## 8. AI 记忆与防漂移

AI 记忆用于帮助定位信息，不作为正式事实数据库。建议将信息区分为：

1. **长期规则：** 项目目标、已批准规范和稳定边界。
2. **当前状态索引：** 活跃任务、当前阶段和状态文件位置。
3. **历史证据指针：** 接受记录、提交、Issue、报告和测试结果。
4. **临时上下文：** 未确认讨论、假设和建议。

重要信息使用明确状态标签，例如 PROPOSED、CONFIRMED、VERIFIED、ACCEPTED、NOT VERIFIED、BLOCKED、SUPERSEDED。标签含义遵循项目既有协议；VERIFIED 不自动等于 ACCEPTED，PROPOSED 不自动成为规则。

新会话恢复流程应尽量短：读取项目状态索引 → 定位 TASK_ID → 读取最新任务状态与有效合同 → 查看相关基线和证据 → 判断当前可执行动作 → 继续推进。若这些资料已足够，不做全项目重复检查；若存在冲突，只核实冲突所需的最小范围。

## 9. 总控与中间层的往返成本

总控应聚焦于授权、范围或合同重大变化、风险决策、跨组冲突、集成和最终接受。中间层可在既有授权内持续推进已批准的读取、诊断、测试、执行包、独立工作包和状态更新，不必每个小步骤都请求再次许可。

遇到需要总控裁定的事项时，中间层应一次性提交事实、证据、影响、可选方案、成本/风险和推荐项；不得以“需要确认”为由反复抛回已经明确授权的事项，也不得把建议性结论写成总控裁决。

## 10. 试点指标

先用现有记录观察，不立即建设新的管理平台或复杂仪表盘。建议选择少量指标：

- 新会话恢复任务所需时间
- 无新增证据的重复核查次数
- 单任务总控往返次数与交付周期
- 阻塞后无条件变化的重复尝试次数
- 交付证据缺失或状态误报次数
- 因范围/交接不清导致的返工
- 授权错误、安全问题与基线回归（必须维持在可接受控制内，不能以效率指标抵消）

效率提升不能以降低验收质量、证据完整性或安全控制为代价。应记录基线值和试点后的变化，避免只凭主观感受宣称改善。

## 11. 分阶段采用

### P0：低成本试点
- 维护一个当前任务状态视图及正式证据链接；
- 采用长期状态、本轮合同、本轮结果的分层交接；
- 新会话按任务恢复，不默认全项目复查；
- READY 工作直接按授权推进，阻塞任务等待明确恢复事件；
- 已接受基线仅在触发条件下复查。

### P1：试点证明有效后
- 记录依赖与准备度；
- 引入与现有政策兼容的风险分级；
- 汇总纠错而非零散重复提示；
- 记录少量效率与质量指标。

### P2：仅在实际需要时
- 自动生成执行合同或结果摘要；
- 自动同步状态和证据指针；
- 事件触发恢复提醒；
- 分析重复返工和等待原因。

优先使用已有仓库、任务记录、Issue/PR 和模板。没有真实需求，不建设新任务平台、复杂状态数据库或 BI 系统。

## 12. 验证与版本治理

本文件是可复用的改进提案，不是已经验证的强制标准。试点应选取目标和合同明确、依赖具备、范围可控且可以实际验证的任务，记录：

1. 任务合同与采用的机制；
2. 恢复时间、往返、重复核查和返工等实际观察；
3. 执行、独立核查和接受证据；
4. 未解决问题、风险及机制带来的额外成本；
5. 是否建议保留、修改或放弃该机制。

完成试点不自动修改现行规范。任何规范性变更都应按目标仓库的版本治理、评审和授权流程提出；在正式批准前，现行标准、任务合同、权限边界和已接受基线继续有效。

## 13. 可复用结论

1. 用持久化状态恢复工作，不依赖对话记忆。
2. 状态卡是索引，不覆盖正式合同和原始证据。
3. 已接受基线默认可信，复查必须有明确触发条件。
4. 长期状态、本轮执行合同、本轮实际结果分开管理。
5. 按授权持续推进，重大决策保留给有权角色。
6. 按依赖并行、按风险治理、按真实证据收口。
7. 先试点、测量、复盘，再决定是否纳入正式标准。

**效率的目标不是让 AI 写出更长的提示词，而是减少无效循环，让人和工具把时间投入尚未完成且真正需要处理的工作。**
