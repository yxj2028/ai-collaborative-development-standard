# AI 协作开发效率优化提案 V1.0（Rev.2）

- **文档状态：** PROPOSED / 待试点验证（提案生命周期状态，不属于任务状态词汇）
- **适用范围：** 可复用于不同软件项目、团队及 AI 协作工具的协同开发流程
- **性质：** 非规范性改进提案；不自动修改现行标准、任务合同、授权或已接受基线
- **形成日期：** 2026-11-04

## 1. 目标与原则

本提案适用于不同项目、团队和 AI 工具。下文出现的记录名称、模板映射和示例只用于说明复用方式；具体项目应映射到自身已批准的等效记录，不要求复制 GSM 的文件名、目录、角色称谓或状态体系。

本提案希望减少 AI 协作开发中的重复核查、重复交接、上下文恢复成本、无效阻塞尝试和人工调度等待，让协作从依赖对话记忆与反复确认，转向**持久状态驱动、实际证据驱动、按依赖并行、按风险治理**。

效率优化不以增加文档、流程、角色或工具数量为目标。优先复用项目已有的任务台账、仓库文档、Issue、PR、执行日志和模板。所有改进必须兼容项目当前的授权与验收规则；未经授权不得变更目标、Contract、共享资源或高风险操作边界。

## 2. 与现行协作职责的兼容

本提案沿用三层责任模型，不增加新的权力层级：

- **Controller / 总控：** 管理目标、授权、优先级、跨组资源与依赖协调、重大变更、集成和最终接受。
- **Middle Layer / 中间层：** 在授权内将任务转成可执行合同，协调执行工具，核查证据、集中纠错、维护状态并向总控提供决策材料。
- **Coding Tool / 执行工具：** 按合同实施并自检，报告实际变更、命令、结果和未完成事项。

效率机制只能减少重复劳动，不能转移最终决策权。中间层不得默默改变目标、验收标准、共享 Contract 或跨组资源决定；执行工具不得扩大范围或自行宣称最终接受。

## 3. 持久化任务状态：复用现有台账，不另建第二套账

建议把任务状态记录作为项目现有任务台账中对应任务的**当前行/摘要视图**，而不是新增独立文件或第二套状态账。若项目没有可用台账，再由有权角色决定最轻量的持久化位置。

状态记录只保留恢复工作所需的信息，并链接到原始合同和证据。可选补充字段包括 WORKSPACE / BRANCH / HEAD、LAST_RESULT、UPDATED_AT；是否增加由项目现有格式和实际需要决定，不得为本提案强制新增字段或模板。

维护责任：Controller 或项目授权的数据/任务负责人维护正式台账；Middle Layer 可提出带证据指针的状态更新，并且只有在明确授权时才直接写入；Coding Tool 只报告实际事实和建议，不自行修改正式台账。状态记录是导航与汇总视图，不是授权、合同、仓库事实或原始证据的替代品。

**建议用于试点的信息权威顺序（非规范性建议，须经各项目治理流程确认后才能成为正式规则）：**
1. 正式授权与有效任务合同：决定允许做什么；
2. 实际仓库、环境和执行结果：决定实际发生了什么；
3. 已接受记录及其证据：确定可信基线和接受状态；
4. 任务台账/状态摘要：索引当前状态，不取代原始事实；
5. 对话历史与 AI 记忆：仅用于定位线索，不作为事实或授权依据。

发生冲突时，记录冲突并核对对应权威来源；不得仅凭摘要或记忆宣布 PASS。## 4. 已接受基线与增量核查

已正式接受的工作应作为后续任务的可信基线。后续任务不应无理由重做、重测或重构前序工作。

仅在出现以下情况时，针对受影响的最小范围重新核查：当前行为与合同冲突、发现回归、当前任务被实际阻塞、明确安全或数据完整性问题，或获得重新审查授权。

处理基线问题采用可追踪的最小闭环：Finding → 影响范围 → 最小修复 → 针对性验证 → 返回当前任务。不得借局部问题扩展为无关重构。此原则不免除当前任务对自身交付物和必要集成验证的责任。

## 5. 三类信息交接：映射到已有记录

长期状态、本轮执行指令和本轮执行结果应在概念上区分，但不意味着必须新增三种文件、模板或字段。优先映射到项目已经批准的记录：

- **TASK_STATUS：** 映射到现有任务台账/任务状态记录，作为当前状态摘要；
- **EXECUTION_TASK：** 映射到现有任务合同或执行任务模板；
- **EXECUTION_RESULT：** 映射到现有关闭/交付报告中的执行事实与验证结果部分。

以上是信息类型映射，不是要求创建同名文件、字段或模板。项目现有记录已能承载信息时，不复制、不另建。

执行结果应按任务风险记录实际执行方、准确工作目录、分支与 HEAD、变更文件、执行命令、测试环境与结果、退出码、失败/跳过/未执行项、证据位置、提交/推送/集成状态、阻塞和下一动作。

严格区分 IMPLEMENTED、SELF-VERIFIED、INDEPENDENTLY-VERIFIED、COMMITTED、PUSHED、INTEGRATED 与 ACCEPTED/CLOSED。前一状态不自动证明后一状态。Coding Tool 负责报告实施、自检、部分完成或阻塞等事实；最终接受仍由 Controller 或项目明确授权的验收角色作出。风险分类和验收权限由项目授权角色确定。

## 6. 状态驱动与事件式恢复

应直接使用项目现有状态词汇，不为采用本提案创造或替换通用状态词。特别要区分 NOT RUN（尚未执行）与 UNKNOWN（当前无法确认）；不能把未执行写成失败，也不能把未知写成未执行。以下仅描述执行策略：

| 当前情形 | 默认动作 |
|---|---|
| 前置条件齐全、可执行 | 进入执行队列，按优先级启动 |
| 正在执行 | 跟踪当前轮次，不重复派发同一工作 |
| 已交付、待核查 | 根据验收标准核验证据 |
| 明确阻塞 | 记录阻塞责任方、受影响范围、恢复条件与恢复后动作 |
| 缺少外部前置条件 | 按项目既有阻塞/暂停流程记录；没有正式暂停决定时，不擅自标记为 ON HOLD；不重复尝试相同失败操作 |
| 已接受/关闭 | 作为可信基线保存，不重新打开，除非触发明确复查条件 |

阻塞记录应简明回答：缺少什么、为何必需、已完成哪些不依赖该条件的工作、哪些操作停止、恢复条件是什么、条件满足后第一步做什么。外部事件等待只有在缺少必要前置条件时才按既有流程标记为 BLOCKED；ON HOLD 仅在有权角色明确作出暂停决定时使用。恢复按项目既有阻塞/暂停/恢复模板和授权门槛执行。出现恢复事件后重新判断是否可执行；无新证据、条件或授权变化时，不重复同一尝试。独立任务可以继续；局部工作包完成不代表整体任务已满足验收。

## 7. 风险匹配与并行准备度

流程重量应匹配任务风险，而不是所有任务采用同等文档和确认成本。本提案不定义新的通用风险等级名称；各项目继续使用自己的风险分类、授权和高风险操作规则。以下仅为控制强度示例，不构成新的分类体系：边界清晰且可回退的工作可采用简洁合同和必要验证；跨模块、接口或数据影响应明确依赖和独立核查范围；权限变更、数据删除/迁移、生产环境和安全敏感操作应遵循既有的明确授权、执行前确认、审计及恢复要求。

并行前至少判断：依赖是否成熟、是否有明确负责人、工作区是否隔离、是否存在文件冲突、共享环境/测试数据由谁协调、接口合同是否稳定。同一文件或共享资源通常应先协调再串行；独立且安全的工作可先行。依赖未成熟时不得猜测接口或越权写入共享环境。并行的目标是缩短依赖等待，而不是同时启动更多工具。

## 8. AI 记忆与防漂移

AI 记忆用于帮助定位信息，不作为正式事实数据库。建议将信息区分为：

1. **长期规则：** 项目目标、已批准规范和稳定边界。
2. **当前状态索引：** 活跃任务、当前阶段和状态文件位置。
3. **历史证据指针：** 接受记录、提交、Issue、报告和测试结果。
4. **临时上下文：** 未确认讨论、假设和建议。

重要信息使用明确状态标签，例如 PROPOSED、CONFIRMED、VERIFIED、ACCEPTED、NOT VERIFIED、BLOCKED、SUPERSEDED。标签含义遵循项目既有协议；VERIFIED 不自动等于 ACCEPTED，PROPOSED 不自动成为规则。

新会话恢复流程应尽量短：读取现有任务台账 → 定位任务与当前轮次 → 读取最新状态和有效合同 → 查看已接受基线及相关证据 → 核对当前实际状态 → 确认已授权的下一动作。若资料已足够，不做全项目重复检查；若存在冲突，只核实冲突所需的最小范围。状态词必须沿用项目定义；NOT RUN 与 UNKNOWN 不得混用。

## 9. 总控与中间层的往返成本

总控应聚焦于授权、范围或合同重大变化、风险决策、跨组冲突、集成和最终接受。中间层可在既有授权内持续推进已批准的读取、诊断、测试、执行包、独立工作包和状态更新，不必每个小步骤都请求再次许可。

遇到需要总控裁定的事项时，中间层应一次性提交事实、证据、影响、可选方案、成本/风险和推荐项；不得以“需要确认”为由反复抛回已经明确授权的事项，也不得把建议性结论写成总控裁决。

## 10. 试点指标与评估设计

先用现有记录观察，不立即建设新的管理平台或复杂仪表盘。试点启动前由有权负责人锁定基线、主要效率指标、目标阈值、质量/安全护栏、样本范围、持续时间和评估责任人；试点中不得为了得到理想结果而追溯修改指标或阈值。确需调整时，应保留原口径并分别报告调整前后结果。

建议选择少量指标：

- 新会话恢复任务所需时间
- 无新增证据的重复核查次数
- 单任务总控往返次数与交付周期
- 阻塞后无条件变化的重复尝试次数
- 交付证据缺失或状态误报次数
- 因范围/交接不清导致的返工
- 授权错误、安全问题与基线回归（必须维持在可接受控制内，不能以效率指标抵消）

效率提升不能以降低验收质量、证据完整性、权限或安全控制为代价。至少 3 个真实任务可用于初步可行性观察，但不能据此宣称普遍有效；正式评估建议覆盖至少 6 个真实任务，并尽可能包含不同团队/项目以及一个跨模块或阻塞恢复场景。样本不足 6 个或高度同质时，只报告局部观察，不作普遍结论。

保留机制的建议条件：预先约定的效率阈值达到，且质量、安全、授权、证据和基线护栏均未恶化。若有效但出现角色混淆、重复记录或额外负担，则修改后再试；若没有可测量收益或护栏恶化，则放弃。应报告样本、实际数据、偏差和局限，不凭主观感受宣称改善。

## 11. 分阶段采用

### P0：低成本试点
- 维护一个当前任务状态视图及正式证据链接；
- 采用长期状态、本轮合同、本轮结果的分层交接；
- 新会话按任务恢复，不默认全项目复查；
- READY 工作直接按授权推进，阻塞任务等待明确恢复事件；
- 已接受基线仅在触发条件下复查。

### P1：试点证明有效后
- 记录依赖与准备度；
- 引入与现有政策兼容的风险分级；
- 汇总纠错而非零散重复提示；
- 记录少量效率与质量指标。

### P2：仅在实际需要时
- 自动生成执行合同或结果摘要；
- 自动同步状态和证据指针；
- 事件触发恢复提醒；
- 分析重复返工和等待原因。

优先使用已有仓库、任务记录、Issue/PR 和模板。没有真实需求，不建设新任务平台、复杂状态数据库或 BI 系统。

## 12. 验证与版本治理

本文件是可复用的改进提案，不是已经验证的强制标准。试点应选取目标和合同明确、依赖具备、范围可控且可以实际验证的任务，记录：

1. 任务合同与采用的机制；
2. 恢复时间、往返、重复核查和返工等实际观察；
3. 执行、独立核查和接受证据；
4. 未解决问题、风险及机制带来的额外成本；
5. 是否建议保留、修改或放弃该机制。

完成试点不自动修改现行规范。任何规范性变更都应按目标仓库的版本治理、评审和授权流程提出；在正式批准前，现行标准、任务合同、权限边界和已接受基线继续有效。

## 13. 可复用结论

1. 用持久化状态恢复工作，不依赖对话记忆。
2. 状态卡是索引，不覆盖正式合同和原始证据。
3. 已接受基线默认可信，复查必须有明确触发条件。
4. 长期状态、本轮执行合同、本轮实际结果分开管理。
5. 按授权持续推进，重大决策保留给有权角色。
6. 按依赖并行、按风险治理、按真实证据收口。
7. 先试点、测量、复盘，再决定是否纳入正式标准。

**效率的目标不是让 AI 写出更长的提示词，而是减少无效循环，让人和工具把时间投入尚未完成且真正需要处理的工作。**


## 14. Rev.2 评审修订记录

- **C1（高）：** 明确任务状态记录复用现有台账，不另建第二套账；明确 Controller/授权负责人、中间层和执行工具的写入责任。
- **C2（高）：** 增加非规范性的信息权威顺序建议，正式采用须经项目治理批准。
- **C3（高）：** 强调沿用项目状态词汇，明确 NOT RUN 与 UNKNOWN 的区别及新会话恢复步骤。
- **C4（中）：** 三类交接信息映射到现有台账、任务合同和关闭报告，不新造模板/字段；最终验收仍归授权角色。
- **C5（中）：** 外部依赖等待按既有阻塞流程处理；ON HOLD 必须来自有权角色明确暂停决定。
- **C6（中）：** 不新增通用风险等级；补充并行准备度检查和共享资源协调要求。
- **C7（低）：** 明确本提案及 proposals 目录内容在正式批准前均为非规范性材料，不改变现行合同、授权或基线；提案生命周期状态与任务状态分离。
- **C8（低）：** 本次不改动现有 PR 分支名，避免在 PR 评审期间引入分支迁移风险；分支命名治理可单独处理，不影响本提案内容。

## 15. 试点决策记录要求

试点结论至少记录：预先锁定的基线和指标、样本与持续时间、各任务实际证据、指标结果、质量/安全护栏结果、偏差与局限、额外流程成本，以及保留/修改/放弃的建议。试点记录不自动赋予提案规范效力。
