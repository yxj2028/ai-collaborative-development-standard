# GSM AI 协作开发效率优化方案 V1.0

- **状态：** PROPOSED / 待试点验证
- **适用范围：** GSM AI 协作开发流程优化
- **性质：** 改进提案；不自动修改现行规范、任务 Contract、授权或已接受基线
- **形成日期：** 2026-11-04

## 1. 目标与判断

GSM 已建立任务授权、Contract、Baseline、执行证据、阻塞管理、职责分离和历史追溯等治理基础。当前主要效率问题逐渐转向重复核查、信息分散、交接过重、任务调度依赖人工确认，以及总控与中间层重复闭环。

目标是将协作方式从“反复核查、反复交接、反复确认”转向：**状态驱动、证据驱动、并行执行、按需治理。**

不以增加文档、流程或工具数量为目标。优先通过轻量状态机制减少重复劳动，同时保持授权、数据安全、Contract 稳定和真实证据要求。

## 2. 职责边界

### GSM-CTRL（总控）
负责目标、正式授权、范围及高风险决策；Contract 变更和基线冲突决策；重大阻塞升级；最终接受、关闭、取消或调整任务。不应每轮重复检查已经有证据支持的执行细节。

### 中间层
在现有授权范围内负责任务状态读取与调度、生成执行工作包、推进 READY 任务及独立工作包、跟踪结果并核验交付证据、更新状态并记录阻塞及恢复条件、提供验收建议。

不得自行扩大授权、修改 Contract、执行未获批准的高风险操作，或将未验证结果标记为 PASS。

### 编程工具
按工作包执行代码修改、测试和 Git 操作，并提供可核验的实际结果。不得自行改变任务目标或边界。

## 3. 唯一有效任务状态来源

每个任务维护一份轻量 Task State，作为当前状态索引；它不取代正式授权、Contract、Baseline 或原始执行证据。

建议字段：TASK_ID、STATUS、CURRENT_OBJECTIVE、AUTHORIZATION、CONTRACT、BASELINE、CURRENT_WORKSPACE、LAST_RESULT、EVIDENCE、BLOCKER、NEXT_ACTION、UPDATED_AT。

### 信息权威性
1. 正式授权和有效 Contract 决定允许做什么。
2. 当前仓库、工作区及真实执行结果决定实际发生了什么。
3. 已接受 Baseline 和正式证据决定哪些工作已可信。
4. Task State 提供状态索引，不得覆盖上述事实。
5. 历史报告、AI 记忆和对话仅提供背景，不得替代当前证据。
6. 推测不得作为正式事实。

如果状态卡写明 PASS，但测试未执行，不能认定 PASS；若状态卡与正式授权冲突，应指出冲突并以正式授权为准。

## 4. 已接受基线与增量核查

前序 Node 已 PASS、CLOSED/PASS 或正式接受后，默认视为 BASELINE。后续任务不重复检查、设计、实现或测试前序 Node。

只有当前实现与历史 Contract 冲突、出现回归或当前任务无法继续、发现明确安全问题、或用户明确要求重新审查时，才重新核查相关部分。核查范围限制在实际受影响的接口、文件、行为或证据，不扩大为全项目复查。

## 5. 三层交接

### 5.1 TASK_STATUS：长期任务状态
每个任务维护一份，回答任务目标、当前状态、已接受内容、剩余工作、阻塞和下一步。只保存当前状态及证据指针，不复制完整历史。

### 5.2 EXECUTION_TASK：本轮执行包
以下字段应简短且明确，尤其要写明执行方和准确工作目录：

```text
TASK_ID:
RECIPIENT:
WORKSPACE:
BASELINE:
OBJECTIVE:
AUTHORIZED_SCOPE:
OUT_OF_SCOPE:
REQUIRED_ACTION:
VERIFY:
DELIVERABLE:
STOP_CONDITION:
```

### 5.3 EXECUTION_RESULT：本轮执行结果
结果应记录 TASK_ID、ROUND_ID、WORKSPACE、BRANCH、HEAD、FILES_CHANGED、COMMANDS_EXECUTED、TEST_RESULTS、EXIT_CODES、GIT_STATUS、COMMIT、PUSH、EVIDENCE、BLOCKER、STATUS、NEXT_ACTION。

明确区分已实现、已执行、已验证、已接受、未执行和被阻塞。不能只依赖自然语言“完成”或“通过”。

## 6. 状态驱动与事件恢复

| 状态 | 含义 | 默认动作 |
|---|---|---|
| READY | 前置条件齐全，可执行 | 优先安排执行 |
| RUNNING | 正在执行 | 跟踪，不重复派单 |
| VERIFYING | 已交付，待核验 | 核验证据 |
| BLOCKED | 存在明确阻塞 | 记录责任方及恢复条件 |
| WAITING | 等待外部事件或依赖 | 等待条件变化，不重复尝试 |
| ACCEPTED | 正式接受 | 作为可信基线 |
| CLOSED | 正式关闭 | 归档状态和证据 |

每个阻塞任务记录 BLOCKER、BLOCKER_OWNER、BLOCKED_SCOPE、REQUIRED_CONDITION、RECOVERY_EVENT、RESUME_ACTION、LAST_CHECKED_AT。

出现恢复事件后，重新判断是否满足 READY 条件。没有新条件时，不重复执行同一失败动作。独立任务不因另一个任务阻塞而自动停止。允许工作包局部完成，但总任务只有满足验收 Contract 后才能标记 PASS。

## 7. 风险分级与流程重量

| 级别 | 特征 | 方式 |
|---|---|---|
| L1 快速执行 | 低风险、边界明确、可回退、独立 | 简化重复检查，直接执行并验证 |
| L2 标准执行 | 多模块、接口或数据结构影响 | 完整 Contract、执行包及结果证据 |
| L3 审慎执行 | 权限、财务、删除、迁移、生产环境、安全边界 | 明确授权、必要的执行前确认、完整审计和验证 |

风险分级减少重复治理，不得削弱必要的授权、安全、数据完整性或审计控制。

## 8. 并行任务与依赖成熟度

任务应明确 DEPENDENCIES（依赖）、READINESS（是否具备执行条件）和 OWNER（唯一执行负责人）。

- 文件和依赖独立时优先并行；
- 接口依赖先确认 Contract；
- 同一文件原则上串行，除非修改区域明确隔离；
- 共享环境、数据库或权限必须明确环境所有权和授权；
- 等待外部条件的任务，可继续推进不依赖该条件的独立工作。

并行不是同时启动更多工具，而是减少依赖等待和工作区冲突。

## 9. AI 记忆与防漂移

AI 记忆用于导航，不是事实数据库。建议分为：
- 永久规则：项目目标、架构原则、工作规范；
- 当前状态索引：当前阶段、活跃任务及状态文件位置；
- 历史证据指针：接受记录、Commit、Issue、报告位置；
- 临时上下文：未确认讨论和推测，不自动升级为事实。

关键结论可使用状态标签：CONFIRMED、ACCEPTED、VERIFIED、NOT_VERIFIED、BLOCKED、SUPERSEDED、PROPOSED。PROPOSED 不自动变为 ACCEPTED；VERIFIED 也不自动代表正式接受。

### 新对话任务入口协议
1. 读取当前项目状态索引。
2. 确定 TASK_ID。
3. 读取该任务最新 TASK_STATUS。
4. 确认当前有效授权和 Contract。
5. 读取本任务需要的 Baseline 与证据。
6. 判断 READY、RUNNING、VERIFYING 或 BLOCKED。
7. 直接执行当前允许的下一步。

状态足够明确时，不进行全项目检查。

## 10. 总控与中间层协作

总控负责目标、授权、重大决策和最终接受；中间层负责授权范围内的持续调度、执行跟踪和证据核验。

中间层无需反复询问是否可以执行已授权的读取、测试、报告更新或独立工作包；但任何授权扩大、Contract 变化、高风险操作或最终接受仍按现行规则处理。

## 11. 效率指标

试点阶段仅记录必要数据，不建设复杂仪表盘：

| 指标 | 观察方向 |
|---|---|
| 有效执行时间占比 | 提高 |
| 无新信息的重复核查次数 | 降低 |
| 单任务总控往返次数 | 降低 |
| 新对话任务恢复时间 | 降低 |
| 无恢复条件的阻塞重复尝试 | 降低 |
| 交付证据缺失率 | 降低 |
| 授权错误 | 保持为零 |
| 因范围误解或信息遗漏导致的返工 | 降低 |

优先观察有效执行时间、重复核查和任务交付周期。

## 12. 分阶段落地

### P0：先试点
- 唯一有效 Task State；
- 三层交接；
- 新对话任务入口协议；
- 已接受基线默认可信；
- READY 优先执行、BLOCKED 等待恢复事件。

### P1：逐步实施
- 任务依赖和成熟度；
- L1/L2/L3 风险分级；
- 明确总控与中间层决策边界；
- 独立工作包局部完成；
- 基础效率指标。

### P2：有真实需求再实施
- 自动生成执行包和交接结果；
- 自动同步任务状态；
- 事件触发恢复提醒；
- 执行效率和返工原因统计；
- 根据试点结果评估自动调度。

不为本方案立即建设新任务管理平台、复杂数据库或 BI 系统。优先使用现有 GitHub、Markdown、任务记录和对话流程。

## 13. 试点与验收

选择一个授权和 Contract 明确、依赖条件具备、工作区独立、范围可控且可验证的任务。

试点验证：
1. 是否能通过 Task State 快速恢复任务，而不重新检查整个项目；
2. 是否能通过执行包直接启动工作；
3. 中间层能否在授权范围内持续推进；
4. 重复核查和总控往返是否减少；
5. 交付证据是否仍满足现行治理要求。

试点得到真实证据后，再决定是否将 P0/P1 内容正式纳入协作规范。试点前，本方案保持 PROPOSED，不自动改变现有规范、任务授权、Contract 或已接受基线。

## 14. 核心原则

1. 一个任务只有一个当前有效状态来源。
2. 已接受基线默认可信，不因新对话重新验证。
3. 长期状态、本轮执行指令、本轮执行结果分开管理。
4. 中间层持续调度，必要决策交给总控。
5. READY 立即执行，BLOCKED 等待恢复事件，独立任务继续并行。
6. 治理重量与任务风险匹配。

效率提升的目标不是生成更长的提示词，而是减少重复工作，把时间集中在尚未完成的工作上。
