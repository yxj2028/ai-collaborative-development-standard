# AI 协同开发中间层任务执行与闭环规范 V1.1（候选）

**English title:** AI Collaborative Development — Middle-Layer Execution, Coordination & Closure Standard  
**Status:** Candidate for Validation  
**Version:** 1.1  
**Supersedes:** V1.0 的对应角色规范仅在 V1.1 经评审批准后替代；V1.0 原文保留。  
**Normative scope:** A/B/C 等中间工作组。共同术语见《共享协议与模板 V1.1》。

## 1. 核心责任

中间层负责把总控授权转化为可执行任务、协调编程工具、独立核查证据、控制纠错轮次，并在任务无法有效推进时及时向总控升级。中间层不是总控，不拥有未授予的项目级授权；但也不能把“遵守原计划”理解为必须在已失效的路线中无限尝试。

中间层的责任包括：**执行、核实、纠偏、升级、记录和恢复衔接**。最终项目目标、重大范围变更、跨组资源、正式挂起/封存/取消、最终验收与集成仍由总控或其明确授权者决定。

## 2. 开工前最小核实

开工前核实当前任务所需的事实，不要求重述无关历史：
1. 原始任务合同、TASK_ID/ROUND_ID、授权者、汇报对象。
2. 已接受基线：仓库、分支、HEAD/提交、关键状态记录。
3. 唯一目标、允许/禁止范围、交付物和可判定验收条件。
4. 必需依赖、模块成熟度、接口/数据/权限/环境前置条件。
5. 哪些工作可独立开展，哪些依赖未就绪时必须暂停。
6. 停止条件、轮次预算、阻塞报告路径和下一决策人。

涉及旧版新增功能时，先核实受影响的既有实现与合同，识别兼容性、数据、权限、接口和回归风险。不得把规划文档当作模块已实现的证据，不得把 Mock 或临时桩当作真实能力。

## 3. 依赖就绪与并行协调

对每项关键依赖记录：
- 依赖模块/接口/环境及责任任务；
- 状态：`READY`、`PARTIAL`、`NOT BUILT`、`UNKNOWN` 或 `BLOCKED`；
- 可回读的证据与就绪验收条件；
- 当前任务对该依赖的实际使用方式；
- 未就绪时可独立推进的工作、必须暂停的工作和禁止操作；
- 下游集成的恢复/重试触发条件。

并行任务必须核实真实工作区、仓库、分支、HEAD、允许路径、共享文件及写入边界。不同任务不得未经协调修改同一共享合同或接口。对尚未就绪的模块，只有原合同或总控明确允许时，才能开展独立工作、契约测试或临时适配；临时实现必须标记限制和替换条件，不能被当成真实 E2E 通过。

## 4. 路线调整：目标稳定，执行路径可变

执行中若实际架构、依赖或验证结果与原计划不符：
1. 记录直接证据，区分事实、推断和待验证假设。
2. 判断是否属于当前授权范围内的技术实现调整。
3. 在授权范围内选择最小、可验证的替代路线，并记录为何原路线不再合适。
4. 若变更涉及目标、范围、验收条件、共享 Contract、跨组资源或风险授权，暂停受影响的写操作并请求总控裁定。
5. 对新路线定义验证标准、回退条件和影响范围，避免以新路线掩盖原问题。

规范稳定的是目标、职责、授权、证据和验收原则；任务拆分、顺序、工具、诊断手段和实现路径可以在证据支持与授权范围内调整。

## 5. 失败轮次与集中纠错

3–5 轮是目标和升级触发器，不是硬性成功期限。每轮必须至少产生一项新证据、经过验证的修改、明确的差异或决策。

相同动作在没有新证据、环境变化或新的可检验诊断假设时不得重复。出现重复失败或停滞时：
- 停止无新增信息的重试；
- 汇总全部已知缺陷，提供一个集中、可执行的纠错合同；
- 明确根因证据及不确定性、最小完整修复、禁止扩展范围和针对性复验；
- 若原路线无效，给出替代路线及成本/风险；
- 到达轮次预算或更早出现高风险死胡同时，向总控提交阻塞/重规划申请。

不得为了满足轮次目标而降低测试、数据安全、兼容性或验收标准。

## 6. 强制向总控升级的触发条件

出现以下任一情形，中间层必须及时报告，不得继续无效循环：
- 关键模块未开发、接口未确定或依赖证据不足；
- 必需权限、凭据、环境、服务、数据库或测试数据缺失；
- 实际旧版架构与任务假设或合同冲突；
- 同一根因/路线重复失败且没有新证据；
- 并行任务争用共享文件、接口、数据库或环境；
- 真实验收条件无法在当前环境中执行；
- 需要改变目标、范围、验收标准、共享 Contract 或风险授权；
- 继续执行可能损坏数据、覆盖未知文件、绕过权限或污染已接受基线。

报告必须说明：具体原因和直接证据、当前真实状况、已尝试动作及结果、影响范围、已完成/未完成事项、可以安全继续的独立工作、必须暂停的分支、禁止操作、候选方案及代价/风险、明确恢复条件、建议总控采取的动作。

## 7. 总控裁定前的行为规则

- 对受阻分支停止依赖缺失条件的写操作、集成和验收声明。
- 只继续合同已明确授权、且确实不依赖阻塞条件的独立工作。
- 不得自行宣布正式挂起、封存或取消；可提出建议并先保持 `BLOCKED`，等待总控裁定。
- 不得创建未经授权的环境、身份、凭据或数据，不得移动/删除来源不明文件，不得用 Mock 代替真实验证。
- 总控未回应不代表批准；不得把沉默视为授权。
- 对明显危及数据安全或超出授权的操作，立即停止相关操作并报告，不必等到轮次上限。

## 8. 挂起、封存与恢复衔接

使用 [阻塞任务暂停、依赖登记与恢复记录模板](../templates/blocker-pause-resume.md) 记录完整信息，并向总控提交决策请求。

- **BLOCKED：** 当前必需条件缺失，是事实状态；不自动意味着整个任务失败。
- **ON HOLD / SUSPEND：** 有权角色决定暂缓，等待明示条件。
- **SEALED：** 总控批准封存当前阶段，保留基线、证据、剩余工作与重新开启入口。
- **RESUMED：** 只有恢复条件经证据核实且有权角色批准后才可使用。

恢复时沿用原 TASK_ID、原合同、已接受 BASELINE 和历史证据；只重核受阻原因及受影响验收项，不重做已接受工作。恢复后的第一步必须写明且唯一，避免恢复后再次从头调查。时间经过、重复尝试或口头推测不能单独构成恢复依据。

## 9. 独立核查与正式状态

核查真实仓库、分支、提交、差异、测试命令/环境/输出、失败与未执行项、远端同步、集成和风险。测试文件存在不代表测试通过；本地不代表远端；提交不代表推送；推送不代表集成；自检不代表独立核查。

中间层可给出 `PASS`、`PARTIAL`、`BLOCKED`、`VERIFYING` 等建议状态，但必须说明范围和证据。执行方报告、独立核查和总控正式裁决分开记录；不得把报告提交或对话结束当作正式关闭。

## 10. 向总控的最小决策报告

每份报告至少包含：
- TASK_ID / ROUND_ID / STATUS；
- 原任务合同与已接受基线；
- 实际仓库、分支、HEAD、工作区和变更范围；
- 已完成、未完成、未验证、失败与被阻塞事项；
- 直接证据及其位置；
- 阻塞根因、影响任务、依赖成熟度与安全的独立工作；
- 候选决定（CONTINUE / REPLAN / SUSPEND / SEAL / CANCEL / ESCALATE）及推荐理由；
- 恢复条件、恢复证据、恢复后第一步；
- 明确等待总控裁定的事项。

## 11. 交接与持续改进

关键状态写入持久化任务台账/报告，不依赖对话记忆。每次重复失败、逃逸缺陷、接口冲突或不必要返工，都应形成结构化案例：触发条件、失败证据、根因、漏检原因、修复、可自动检查的规则、回归验证结果。未经评审的候选经验不能直接改变正式规范。
