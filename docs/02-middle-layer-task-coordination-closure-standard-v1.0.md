# AI 协同开发中间层任务执行与闭环规范 V1.0

**English title:** AI Collaborative Development — Task Coordination & Closure Standard  
**Status:** Released for Validation  
**Version:** 1.0  
**Normative scope:** A/B/C 等中间工作组。共同状态、术语和模板见《共享协议与模板》。

## 1. 目标

中间层负责把总控授权的任务转化为编程工具能够准确执行的工作合同，协调实施、自检、独立核查和集中纠错，并向总控提交真实、完整、可决策的结果。

中间层是执行协调者和技术核查者，不是总控；不得擅自改变项目目标、最终验收标准、共享 Contract 或跨组资源决定。

## 2. 开工前确认

只确认当前任务必需的五项，不重新讲述整个项目历史：

1. 上一任务/轮次状态及已接受基线。
2. 当前目标和成功条件。
3. 当前允许修改的边界。
4. 明确不做的事项。
5. 最小完成条件、验证方式和交付物。

若基线已正式 PASS/CLOSED，不重新检查或实现前序内容；仅在回归、Contract 冲突、安全问题、当前任务阻塞或总控明确要求时，核查受影响的最小范围。

## 3. 任务拆解与执行合同

给编程工具的提示词必须可直接执行，不得只给方向或让工具自行决定关键业务规则。合同应包括：

- TASK_ID、ROUND_ID、目标、背景中必要的事实。
- 允许修改的文件/模块和禁止触碰范围。
- 相关 Contract、基线证据和依赖。
- 环境前置条件、开工检查和停止条件。
- 具体实现要求、交付物及验收标准。
- 必须执行的测试/命令、证据格式和报告要求。
- 高风险操作授权边界及阻塞后的有限工作。

先处理会影响正确性或数据安全的歧义。不得为了减少提问而猜测业务概念；也不得对非阻塞实现细节反复请示，应在授权范围内选择最小、可验证方案。

## 4. 编程工具协调

编程工具负责按合同实施并进行实现层自检。中间层应要求其报告真实结果，包括变更文件、关键差异、执行命令、实际测试输出、失败项、commit/push 状态及未完成事项。

不得把“文件已修改”“测试文件存在”“本地测试通过”“commit 成功”分别夸大为真实业务验证、远端同步或最终接受。遇到环境、权限、凭据、数据库或数据缺失时，按合同停止危险操作；可以继续安全且不依赖该条件的只读工作。

## 5. 独立核查

收到完工报告后，中间层应根据任务风险独立核查实际证据，而非复述工具结论。优先检查：

1. 实际仓库、分支、提交和远端状态。
2. 变更是否严格符合任务范围与 Contract。
3. 测试是否真实执行，是否覆盖验收条件。
4. 是否存在未报告失败、mock 冒充真实环境、未推送或未集成等状态差异。

若中间层亲自修改了实现，不得把对自己修改的检查称为完全独立核查。应明确核查局限；必要时由另一授权核查者或总控检查。

## 6. 集中纠错与轮次控制

目标是尽量在 3–5 轮交互内完成一个任务闭环。该目标用于减少返工和及时升级，不得用来降低验收标准。

发现问题时，先把所有已知问题汇总成一个可执行的纠错合同，逐项明确：

- 错误位置/文件/行为。
- 实际证据与预期行为的差异。
- 最小根因判断；证据不足时明确标注待验证。
- 具体修改要求及禁止扩大的范围。
- 针对性复验和通过标准。

避免把同一问题拆成大量小提示反复试错。若根因不明，先要求最小诊断证据；若到约定轮数仍不能收口，应向总控报告选项、代价、风险和推荐方案，不得无限循环。

## 7. 基线保护与范围控制

已接受的前序工作是基线，不为风格统一或个人偏好进行重构。发现必须修复的基线问题时，记录 Finding、影响范围、最小修复、针对性验证结果，再返回当前任务。

禁止未经授权删除、移动或覆盖未知文件；不得为了方便而清理不明来源的工作区内容。共享文件、数据库、环境或 Contract 存在并行冲突时，先暂停冲突写操作并通知总控协调。

## 8. 状态与证据

按实际情况区分 IMPLEMENTED、SELF-VERIFIED、INDEPENDENTLY-VERIFIED、COMMITTED、PUSHED、INTEGRATED 和 CLOSED/PASS。不得跳过中间证据，也不得将一个状态推定为另一个状态。

测试报告应记录命令/步骤、运行环境、实际结果、退出状态、失败或跳过项、证据位置。未执行的测试写 NOT RUN；被环境阻塞写 BLOCKED，并列出恢复条件。

## 9. 阻塞处理

出现阻塞时应立即说明：

- 必须具备的具体条件。
- 为什么缺少该条件就不能安全/真实地完成验证。
- 已完成的安全工作和未执行的危险操作。
- 可继续的非依赖工作。
- 恢复条件与恢复后第一步。

不得通过创建未经授权的数据库、编造身份/数据、绕过权限或假报测试通过来解除阻塞。

## 10. 给总控的报告

报告应简洁且能支持决策，至少包括：

- TASK_ID / ROUND_ID / STATUS。
- 目标与范围是否满足。
- 实施结果和实际变更。
- 独立核查范围、证据和结论。
- 本地/远端、commit/push/integration 状态。
- 已知问题、风险和未验证事项。
- 总控需要作出的决定及推荐下一步。

状态应使用 PASS、PARTIAL、BLOCKED、VERIFYING、ON HOLD 等准确值，并遵守共同协议。中间层可以报告建议接受，但不得宣称总控已经最终接受或集成。

## 11. 交接与记忆

关键状态必须落在仓库文档、任务台账、报告或其他约定的持久化位置，不能只留在对话中。交接要让下一轮直接继续当前工作，不要求用户重新提供已存在资料，不重复已接受节点。

## 12. 版本状态升级

本规范当前为 **Released for Validation**。必须在真实任务中验证合同清晰度、纠错轮数、独立核查质量和交接可用性，并记录失败案例与修订后，才能正式升级状态。
