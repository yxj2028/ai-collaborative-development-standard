# AI 协同开发总控与任务调度规范 V1.0

**English title:** AI Collaborative Development — Controller & Task Orchestration Standard  
**Status:** Released for Validation  
**Version:** 1.0  
**Normative scope:** 总控角色。共同状态、术语和模板见《共享协议与模板》。

## 1. 目标

确保 AI 协同开发围绕明确的项目目标推进；任务可授权、可追踪、可并行、可验收；出现依赖、冲突或阻塞时，由有权角色作出决定，而不是让执行层猜测。

本规范定义总控如何管理任务，不规定具体行业业务，也不要求总控亲自编写所有代码。

## 2. 总控职责

总控对以下事项保留最终决定权：

1. 项目目标、优先级、范围和关键验收标准。
2. 任务授权、任务拆分边界、跨组并行关系及共享资源协调。
3. 关键 Contract、数据边界、安全风险和集成风险的裁定。
4. 任务继续、重规划、挂起、中止、接受、拒绝或集成的决定。
5. 项目级状态台账和正式交接记录的完整性。

总控可以委派具体技术执行和证据检查，但不得把最终项目决策责任隐式转移给中间层或编程工具。

## 3. 任务授权与合同

每项工作开始前，确保执行方获得一份可执行的任务合同，至少明确：

- TASK_ID、任务目标及当前轮次。
- 允许修改的范围、明确排除项及相关文件/模块。
- 输入、已确认基线、依赖和环境前置条件。
- 交付物、验收标准和必须提供的证据。
- 高风险操作限制、停止条件、阻塞后的有限工作。
- 汇报对象、下一决策人和交接格式。

任务合同必须足够明确，避免执行方自行猜测业务含义、权限边界或验收标准。若合同存在影响正确性的重要歧义，应在开工前澄清；非阻塞的实现细节可在授权范围内由中间层决定。

## 4. 并行任务调度

总控可以按 A/B/C 等工作组并行分配任务，但每组必须拥有清晰边界。分配前检查：

1. 是否修改同一文件、共享 Contract、同一数据库或同一环境。
2. 是否存在前置任务、环境、凭据、测试数据或权限依赖。
3. 并行任务之间是否有写入冲突、验证冲突或资源争用。
4. 每项任务失败或阻塞时，其他任务是否可以安全继续。

对共享资源和跨组冲突，由总控指定唯一协调者和处理顺序。不得因任务并行而允许多个执行方未经协调修改同一共享 Contract。

## 5. 状态台账

总控维护可持久化的项目/任务台账，不依赖聊天记录作为唯一记忆。每项任务至少记录：

- 目标、范围、负责人/执行组、TASK_ID 和当前 ROUND_ID。
- 状态、依赖、基线及 Contract 位置。
- 已完成工作、剩余工作、阻塞原因和恢复条件。
- 验证命令/步骤、实际结果、证据位置及核查者。
- commit、push、integration 和 acceptance 的分别状态。
- 总控决定、决定依据、下一动作及交接对象。

台账应更新为当前事实；不得把计划、工具声称或本地状态写成已经验证的远端事实。

## 6. 证据与验收

总控根据风险确定所需独立证据，重点检查：

- 目标分支和远端实际状态是否符合任务合同。
- 测试是否真实执行，命令、环境、退出码和结果是否可追踪。
- 关键业务路径是否有真实验证，而非仅有测试文件或 mock 结果。
- 重要数据、权限、迁移、回滚和共享 Contract 是否存在风险。
- 交付物是否与任务目标一致，是否存在未披露的范围偏离。

状态必须严格区分：已实现、自检通过、独立核查通过、已提交、已推送、已集成、总控接受。前一状态不自动证明后一状态。

总控不必重复所有低风险测试，但应对高风险、共享 Contract、远端差异、独立验证证据和集成结果作出有根据的判断。

## 7. 基线与防漂移

已经正式接受的前序任务作为 BASELINE。后续任务不得无理由重做或重构。只有在发现回归、Contract 冲突、安全问题、当前任务被阻塞，或收到明确重新审查授权时，才重新打开相关范围。

若需要修复基线，应记录：Finding → 影响 → 最小修复 → 针对性验证 → 恢复当前任务。不得借局部问题扩展为无关重构。

## 8. 迭代效率与升级

3–5 轮交互是控制沟通成本的目标和升级触发器，不是降低质量的截止线。若在约定轮数内未能收口，总控应要求提交具体失败证据，并决定集中修复、重新规划、分拆依赖或挂起；不得无限重复含糊提示。

## 9. 阻塞、挂起与中止

阻塞报告必须说明：缺少什么、为什么必需、已经完成哪些不依赖该条件的工作、哪些操作已停止、恢复条件是什么。不得以猜测补造环境、数据、权限或测试结果。

总控根据风险与价值决定继续、挂起或中止，并在台账记录原因和恢复条件。环境未满足时，允许执行安全的只读调查和准备工作，但不得绕过明确停止条件。

## 10. 安全与高风险操作

删除重要数据、修改已验收或已结算数据、变更金额、权限、负责人、数据库、生产环境或大范围文件等操作，应有明确授权、备份/回滚策略和可追踪证据。执行层无权以“方便实现”为由扩大授权。

## 11. 最终决策与交接

总控根据交付物、独立证据、遗留问题和风险，明确给出以下之一：ACCEPTED、REJECTED、BLOCKED、ON HOLD、CANCELLED 或已批准集成。未满足验收条件时不得以代码已完成、已提交或已推送替代接受。

每次交接至少包括项目/阶段、任务及轮次、前序状态、已接受基线、目标与边界、Contract、文件范围、测试证据、已知问题、总控决定和下一动作。

## 12. 版本状态升级

本规范当前为 **Released for Validation**。只有在真实任务中记录执行结果、暴露问题、完成必要修订，并经正式评审后，才能升级状态。不得仅因文档写完就宣称成熟或已验证。
