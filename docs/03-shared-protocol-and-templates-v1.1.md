# AI 协同开发共享协议与模板 V1.1（候选）

**Status:** Candidate for Validation  
**Version:** 1.1  
**Purpose:** 统一角色边界、状态语义、依赖成熟度、阻塞升级、挂起/封存/恢复与证据要求。  
**Compatibility:** V1.0 保留为历史基线；V1.1 经评审批准前，不得宣称已正式替代 V1.0。

## 1. 三层责任与授权边界

| 角色 | 负责 | 不得擅自决定 |
|---|---|---|
| Controller / 总控 | 目标、授权、优先级、跨组协调、依赖冲突裁定、任务生命周期决定、最终验收与集成 | 不得把最终决策责任隐式下放 |
| Middle Layer / 中间层工作组 | 任务拆解、依赖与旧版影响核实、工具协调、独立核查、失败诊断、阻塞升级、执行已授权的纠偏、恢复衔接 | 不得擅自改变目标、验收标准、共享合同、跨组资源或正式封存/取消决定 |
| Coding Tool / 编程工具 | 按合同实现、自检、报告证据与阻塞 | 不得扩大范围、绕过授权、把未知猜成事实或自行宣称正式接受 |

本协作模型为三个责任层级，不增加第四层。A/B/C 是并行工作组标识，不改变权限边界。

## 2. 规范原则与执行策略分离

**稳定的治理原则：** 项目目标、授权、角色边界、数据安全、证据真实性、验收责任和变更批准规则。

**可基于证据调整的执行策略：** 任务拆分、依赖顺序、并行/串行方式、实现路线、诊断手段、工具选择和验证顺序。

执行计划不是不可更改的命令。发现原路线无效时，必须在授权边界内调整或向总控申请裁定；不能借“规范固定”拒绝纠偏，也不能借“路线调整”突破目标和授权。

## 3. 统一任务标识与基线

- `TASK_ID`：任务稳定身份；恢复时原则上沿用，不为同一任务无故另建身份。
- `ROUND_ID`：本轮执行/纠错编号。
- `PARENT_TASK`：父任务或授权来源。
- `CONTRACT_REF`：当前正式任务合同位置。
- `BASELINE_REF`：已接受的代码、提交、版本和证据基线。
- `BLOCKER_ID`：可独立追踪的阻塞记录身份。
- `DECISION_REF`：总控或有权角色的裁定记录。
- `RECOVERY_TRIGGER`：触发重新检查阻塞条件的明确事件/证据。

必须沿用项目已有编号规则，不得为套用模板重写历史身份。

## 4. 状态必须分维度记录

### 4.1 执行/交付状态

`PLANNED`、`IN PROGRESS`、`IMPLEMENTED`、`SELF-VERIFIED`、`INDEPENDENTLY-VERIFIED`、`COMMITTED`、`PUSHED`、`INTEGRATED`、`ACCEPTED`、`REJECTED`。

### 4.2 生命周期/阻塞状态

`ACTIVE`、`BLOCKED`、`ON HOLD`、`SEALED`、`CANCELLED`、`CLOSED`。

### 4.3 依赖成熟度

`READY`（有证据证明满足使用条件）、`PARTIAL`（部分能力已具备）、`NOT BUILT`（确认尚未开发）、`UNKNOWN`（事实未知）、`BLOCKED`（存在具体阻塞）。

不同维度不得压成单一状态。一个任务可以“部分交付已验证，但整体仍 BLOCKED”；某个子分支可以暂停而不影响明确独立的工作。状态必须带范围和证据。

状态不可互相推定：实现不代表测试通过；自检不代表独立核查；提交不代表推送；推送不代表集成；任何技术状态都不自动代表正式接受。封存不代表完成或取消。

## 5. 阻塞升级协议

以下任一条件触发中间层正式向总控报告：
- 关键依赖未开发/未就绪；
- 环境、权限、凭据、服务、数据或真实验证条件缺失；
- 旧版实际架构与合同假设冲突；
- 相同失败路径在无新证据时重复；
- 并行任务发生共享资源/接口/文件冲突；
- 需要改变目标、范围、验收、共享合同或风险授权；
- 继续可能破坏数据、未知文件或已接受基线。

阻塞报告必须含：直接证据、具体缺失条件、根因（事实/推断分开）、已尝试动作及结果、影响范围、可独立继续/必须暂停/禁止执行的分流、候选方案及成本风险、建议总控决定、恢复条件和恢复后第一步。

中间层提交报告后，受阻分支保持 `BLOCKED`，等待有权角色裁定；总控未回应不构成批准。只有合同明确授权且不依赖阻塞条件的安全独立工作可以继续。不得擅自宣布正式 `ON HOLD`、`SEALED` 或 `CANCELLED`。

## 6. 总控生命周期决定

| 决定 | 含义 | 必须记录 |
|---|---|---|
| `CONTINUE` | 原条件成立，继续原合同 | 决策依据、下一动作 |
| `REPLAN` | 批准在目标不变前提下调整路线/依赖/任务拆分 | 新路线、边界、验证和回退条件 |
| `SUSPEND` / `ON HOLD` | 暂缓，等待条件成熟 | 明确触发条件、责任人、复查方式 |
| `SEAL` / `SEALED` | 封存当前阶段，保留重启入口 | 基线、证据、未完成项、重新开启条件 |
| `CANCEL` / `CANCELLED` | 取消任务 | 原因、影响、后续依赖处置 |
| `ESCALATE` | 请求更高权限或项目级裁定 | 需决策问题、风险、候选方案 |
| `ACCEPT` / `REJECT` | 正式验收决定 | 对照验收标准的证据与理由 |
| `APPROVE INTEGRATION` | 批准进入指定集成分支/环境 | 目标、基线、检查和回滚条件 |

总控裁定必须持久化到台账或决策记录，并关联原 TASK_ID、BLOCKER_ID 和合同。决定可包含条件，但条件必须可核验。

## 7. 恢复门槛

恢复前全部满足：
1. 必需依赖、权限、环境和数据实际可用；
2. 恢复证据可回读、可核验；
3. 证据覆盖原阻塞原因及受影响验收项；
4. 有权角色明确批准恢复；
5. 原合同、已接受基线和剩余工作已重新对齐；
6. 已明确恢复后的唯一第一步和禁止重做项。

单纯时间经过、超时、重试次数或猜测不构成恢复条件。恢复沿用原 TASK_ID、合同、证据与已接受基线，只处理未完成项；若合同实质变化，则先完成变更审批。禁止自动重启受阻写操作。

## 8. 轮次控制与防空转

3–5 轮为目标与升级触发器。每轮必须产出新证据、经验证的修复、清晰差异或决策。无新增证据/环境变化/新诊断假设时，不重复同一动作。出现高风险或明显死胡同时可以提前升级，不必等满轮次。不得以控制轮数为由降低验收标准。

## 9. 旧版增量开发与并行依赖

在旧版上新增功能时，任务合同必须识别受影响的既有模块、接口、数据、权限、配置和回归边界；只检查与当前任务相关的范围。既有已接受能力默认作为基线保护，不重做无关工作。

并行任务必须记录上游/下游依赖、接口契约、文件/模块所有权、集成责任和就绪条件。计划存在不代表实现存在；临时接口/Mock 必须明确标注，不能冒充真实业务完成。局部通过不代表集成通过。

## 10. 证据与持久化

证据至少记录：仓库、分支、HEAD/提交、工作区状态、文件差异、命令/步骤、环境、实际输出/退出码、失败/跳过/NOT RUN 项、远端与集成状态、独立核查者和限制。未知写 `UNKNOWN`，未执行写 `NOT RUN`，缺少必需条件写 `BLOCKED`，不适用写 `N/A`。

重要状态必须保存在仓库、任务台账、报告或决策记录，不得仅存在对话中。未知来源文件不得未经授权删除、移动或覆盖。

## 11. 持续改进与评估

真实任务中的重复失败、纠错轮数过多、逃逸缺陷、旧功能回归和并行冲突应转成可复现回归案例。每个改进候选记录：问题/触发条件、原行为、候选变化、验证案例、结果、成本与副作用、批准状态。

建议按任务类型与风险等级记录：
- 首轮/首次提交验收通过率；
- 平均纠错轮数和超出 5 轮的任务比例；
- 独立核查发现的问题率与生产/集成逃逸缺陷率；
- 证据完整率、依赖未就绪导致的返工；
- 历史回归案例拦截率；
- 每任务耗时与执行成本。

指标必须注明分母、时间窗口、任务类型和缺失数据。轮数下降但逃逸缺陷率上升不算改进。模型自评、执行轨迹或单个成功案例不能独自证明候选规则有效。正式标准的变更必须评审和授权。
